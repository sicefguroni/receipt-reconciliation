## Dataset

One synthetic month (October 2026), generated by `pnpm dataset` and committed under `fixtures/dataset/`: 40 receipts in 6 layouts (23 PDF, 14 phone-photo JPEG, 3 PNG) and 44 statement lines, 9 of which have no receipt. All vendors, people, and amounts are fictional.

- **Ground truth** (`ground-truth.json`) is written by hand from each scenario's intent and never computed by `src/core`; otherwise the eval would grade the rules against themselves.
- **Splits:** `tuning` (24 receipts) may be used to set thresholds; `holdout` (16) is never looked at while tuning. The split is stratified so both halves contain hard cases. Numbers are reported on the evaluated set and on its holdout part.
- **Baseline subset:** 20 receipts used for B0 and B1, including TC04, TC06, TC07, and TC11.

## Pass/fail rubric

**A test case passes only if every expected behaviour in its row holds for every receipt that carries it.** Partial is a fail, and the report lists each failed assertion. The assertions, as implemented in [`scripts/eval/system.ts`](../scripts/eval/system.ts):

| TC | Every one of these must hold |
|---|---|
| TC01 | Auto-matched to the correct line; correct category; in the bulk-approve group |
| TC02 | Matched to the correct line; converted with a stored rate; no amount-difference flag; ledger amount equals the AUD charged |
| TC03 | Currency read as AUD; never entered FX conversion; included in totals |
| TC04 | Before a decision: `ambiguous`, `AMBIGUOUS_MATCH`, and the $560 line offered as a candidate. After the expected human choice of that line: `AMOUNT_DIFFERS_OVER_THRESHOLD`, and approval is blocked until a reason is given |
| TC05 | Matched to the correct line; a +$2.00 difference badge; bulk-approvable with no reason |
| TC06 | `MISSING_PURPOSE` on both; approval blocked |
| TC07 | Each copy: `DUPLICATE`, pointing at the original, excluded from totals. The original: not flagged, included in totals |
| TC08, TC09 | Passes the quality gate; total, currency, and date extracted correctly |
| TC10 | `unmatched`; offered as a reimbursement; not flagged `NO_PAYMENT_FOUND` |
| TC11 | `ambiguous`, never auto-picked; both twin lines ranked as candidates |
| TC12 | The expected category; never "Other" |

**The system passes v1** if all of the following hold:

1. TC01–TC12 all pass.
2. Exception recall is 100% for the TC04, TC06, and TC07 codes on the full set.
3. The wrong auto-match rate is 0% on holdout.
4. Extraction total and currency accuracy are each ≥ 95% on holdout.

If the system misses the bar, it still ships, and this document states the miss, its root cause, and the next step.

## Metrics as computed

| Metric | Definition |
|---|---|
| Extraction accuracy | Per field: total within $0.01; currency exact; date exact; vendor normalised fuzzy match ≥ 0.8 |
| Category accuracy | Exact category before human review |
| Match recall | Receipts whose correct line is the auto-match or the top-1 candidate, over receipts that have a correct line |
| Wrong auto-match rate | Auto-matches to the wrong line, over all auto-matches. Ambiguous items are not auto-matches: they go to a person |
| Exception recall / precision | Per code, fired vs expected, after the expected human match choice (so TC04 is scored on its over-threshold flag) |
| Human touches | Receipts not in the bulk-approve group, over all receipts. Statement lines with no receipt are counted separately. Best possible on October: 9/40 (22.5%) |
| No-receipt line recall | Lines listed as "No receipt" after the expected match decisions, over the 9 true ones (full set only) |
| Latency, tokens, cost | From the run log. Replay reports the numbers recorded in the live run. Cost is an upper bound: all input tokens at the full rate (`config/pricing.json`) |

### Stress set (Day 4)

`pnpm eval:stress -- --mode replay --label <name>`. Ten cases from the `06` list, each built to hit one mechanism, kept apart from the October month so earlier runs stay comparable (`fixtures/stress/`, generated by `pnpm dataset:stress`). S09 and S10 reuse the October data. A case **passes when the system fails safely**: the right answer (*correct*), or wrong or unsure but routed to a person (*safe*). A silent wrong value, a wrong pairing, or a rejected valid input is a *failure*.

| ID | Stress case (from `06`) | Before (`v2-day4-pre-stress-2`, live) | After (`v2-day4-post-stress`) |
|---|---|---|---|
| S01 | Unreadable photo, 300 × 400 | correct: stopped at the gate, never sent to the model | correct |
| S02 | Heavy blur at full size (passes the gate) | safe: every field null at confidence 0, flagged | safe |
| S03 | Chat screenshot | **failure**: rejected as "retake it closer" | correct: `NOT_A_RECEIPT` |
| S04 | Bare "$", no currency clues | safe: currency left blank, flagged (never assumed AUD) | safe |
| S05 | `10/09/2026` on a US invoice | correct: read as 9 October | correct |
| S06 | One receipt paid in two transactions | safe: `ambiguous`, both part payments kept visible | safe |
| S07 | Purchase later refunded | **failure**: the refund offered as a candidate | correct |
| S08 | Only the refund on the statement | **failure**: the refund was the top candidate | correct: `NO_PAYMENT_FOUND` |
| S09 | Statement with a title row and ISO dates | **failure**: rejected | correct: 44 lines identical |
| S10 | FX API unreachable | safe, but over-flagged and a contradictory summary | correct |
| S11 | Statement with US-style (month-first) dates *(added 2026-11-04)* | **failure**: full month rejected; a 1–12 October excerpt read with 15 of 18 dates wrong, silently (measured on the Day 4 reader) | correct: 44 lines identical, "dates read month first" shown |

Every failure was in the rules or data contracts, not in perception: on blur, a bare "$", and an ambiguous date, the model said it was unsure or got it right. The stress run was recorded live twice (`v2-day4-pre-stress`, `-2`; at most USD 0.043 and 0.045, 6,022–6,023 input tokens each) with the same outcomes; two date confidences moved between runs (0.99 → 0.75, 0.95 → 0.75), so one live run can change the human-touch count by one or two. S06 is *safe*, and since 2026-11-04 also resolvable: R-MAT-10 lets a person pay one receipt from several lines, compared on their sum. Before that, the reviewer had to sign off a false difference against one part and record the other as a substitute. The *after* column for S01–S10 is `v2-day4-post-stress`; S11 is `v2-day4-followup-stress`.

**Browser check (2026-11-04).** The refund wording and the split payment were checked on a production build with `fixtures/stress/statement-october-split-and-refund.csv`: 16 of 16 checks pass (details in `failures.md`, "Follow-up"). The screenshots led to two fixes no test had caught: negative amounts printed as "$-4.50", and a split form that listed every free line under each receipt.

### Oracle: the rules alone

`pnpm eval -- --mode oracle --label oracle-day2` feeds the ground-truth fields in place of the model, so it measures the rules and pipeline without perception. Result: 12/12 test cases and identical match, exception, and human-touch numbers to v0-day2. So every remaining error in a live run is a perception error, not a rules error, on this set. Building this mode caught one rules bug before any live run: a stationer's mixed basket ("Desk organiser") categorised as Equipment (fixed; see the TRACKER AI corrections log).

Read with care:

- **B1 is strong.** On clean synthetic receipts it reads, categorises, and finds payments as well as the system. The difference is correctness of the ledger: B1 assigned one $312 payment to an original and both of its duplicates, and paired a hotel receipt that has no payment with a different hotel stay's charge (29% off), in every run. The system assigns each line at most once and sends doubtful pairings to a person.
- **B0 accuracy is not measured.** The Accounting user was unavailable on Day 1, and the candidate had seen the answer key. The time is a labelled estimate.
- **The system's wrong-match denominator is smaller (14 vs 19)** because it auto-matches fewer receipts: ambiguous and duplicate items go to a person instead. That is the design, and it costs human touches (8/20 on this subset).
- On this subset v0 passed 10 of 11 test cases; the miss (TC10, R13) was the date-gate finding below, fixed on Day 4 (F6), and v2 passes 11/11.
- Human touches on the subset (40%) are above the 35% target because the subset over-samples hard cases on purpose (TC04, TC06, TC07, TC11). On the full month the rate is 23%.

## Builder cold run (C1, Day 4)

The candidate closed the October month from a fresh clone in **about 8 minutes** (install 17.3 s). Scored against the key: 37 of 40 receipts right. The 3 misses were all pairings the person chose and signed off as "Good" (a $14.70 coffee with a $75.20 petrol charge, a $19.99 app with a $34.95 bookshop charge, a $268 hotel with a $31.20 taxi), so the ledger was **$106.66 over** the ground truth. Every automatic match was correct. This is the first evidence that the risk is not only the model or the rules: the human step needs a guardrail too. Changes made in response are in `sprint/days/day-3-working-core/first-run-observations.md`. One person, the builder, so it is a floor, not usability evidence; P1 is the test for someone else.

## Proxy run (P1, Day 4)

Someone with a year of business-management experience, new to the app, closed the October month in **9 minutes** with help once (when and what was not recorded), on commit `db8579c`. Scored against the key: **39 of 40**; the one miss was again a pairing the person chose: the $268 hotel (R20, no payment on the statement) with the $10 monthly card fee, signed off "This is good", **with the pairing check on screen**. Ledger **$10.00 over**. Every automatic match was correct.

What the two runs show together:

| | C1 (builder) | P1 (proxy) |
|---|---|---|
| Build | `4b537cd`, no pairing check | `db8579c`, pairing check, specific reasons |
| Time to close (target ≤ 10 min) | about 8 min | 9 min, assisted once |
| Receipts right | 37 / 40 | 39 / 40 |
| Ledger vs ground truth | $106.66 over | $10.00 over |
| Wrong automatic matches | 0 | 0 |

The difference cannot be credited to the pairing check: different people, builds, and help. Both runs say the same thing: **the system's own matching was right every time; every wrong number came from a person pairing a receipt with an unrelated payment.** A screenshot of P1's screen showed why: for a receipt with no real candidate, the payment list filled up with weak lines, and the card fee was the first one offered. Changes made in response (R-MAT-11, only real candidates suggested, on-page tabs, light cards) are listed with their checks in `sprint/days/day-4-evaluate-and-harden/feedback-session.md`. Whether they change what a person does has not been measured: that needs another run.

## Known measurement artifact

Per-code recall for `AMBIGUOUS_MATCH` reads 0/1 in every run since `v0-day2`. Per-code recall is scored after the simulated expected human choice, which removes R15's ambiguity by construction; it is not a system miss. TC11 checks the ambiguity directly, before any choice, and passes in every run. The headline exception recall does not include this code. Left unchanged so the metric stays comparable across runs.

## Day 2 findings (fixed on Day 4)

Found on Day 2 and left alone until Day 4, because `06` reserves threshold and scoring changes for Day 4, tuned on the tuning split, with a before/after comparison. Both are now fixed: F5 and F6 in `failures.md`.

1. **Wordmark vendor names lose the vendor points.** On both ad-platform invoices (R16, R30, tuning split) the model returned the logo text `brightreachads`. It shares no word with the statement's `BRIGHTREACH ADS`, so the pairs score 80 instead of 100. They still auto-match only because no competing line exists. Root cause: the prompt says "as printed", and the most prominent print is a logo.
2. **The scoring table has no date gate.** Run on the 20-receipt subset, R13 (a $14.70 personal-card coffee with no statement line) is pushed to `ambiguous` by a $15.50 café line dated 15 days earlier: +30 for an amount within 10%, and +10 for the shared word "cafe", which makes 40. In the full month another receipt takes that line first. This fails safe (an extra human touch, not a wrong match), but in a real month free lines are normal.

## How to run

```bash
pnpm eval -- --mode replay --label <name>                # full set, no API key
pnpm eval -- --mode replay --label <name> --cases TC04   # a subset (also --ids R01,R02)
pnpm eval -- --mode live   --label <name>                # real calls; records new fixtures
pnpm eval -- --mode oracle --label <name>                # ground-truth fields: the rules alone
pnpm eval:compare -- <labelA> <labelB>                   # metric deltas, regressions flagged
pnpm eval:stress -- --mode replay --label <name>         # the 10 stress cases, no API key
pnpm eval:stress -- --mode live --label <name> --ids S03 # record chosen stress receipts only
pnpm dataset:stress                                      # regenerate fixtures/stress
```

Each run writes `eval-results/<label>/summary.json`, `cases.csv` (one row per receipt, expected vs actual), and `report.md` (TC table, metrics, every failed assertion).
